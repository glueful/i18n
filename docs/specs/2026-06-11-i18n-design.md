# Glueful i18n Extension Spec

**Status:** Draft v2  
**Package:** `glueful/i18n`  
**Purpose:** Localization primitives for Glueful apps and extensions.
**Framework floor:** `glueful/framework >=1.54.0`

## Summary

`glueful/i18n` provides locale management, translation catalogs, fallback rules, and regional formatting for Glueful apps.

It should formalize and extend the framework's existing message-catalog behavior. It should not replace every app's domain-specific localization model. For example, Lemma content localization should build on this extension, but Lemma still owns localized entries, fields, slugs, and publishing workflow.

## Boundary

### Core Should Own

Core currently has `ServiceProvider::loadMessageCatalogs($dir, $domain)`, which looks for a string-keyed `translation.manager` service and calls `addMessages($locale, $domain, $messages)`. The framework does not currently expose a formal translator or locale resolver contract.

This extension should first satisfy the existing framework hook by binding `translation.manager`. Contracts should ship in the extension namespace first; a later framework cleanup can formalize typed aliases if a core consumer appears:

```php
namespace Glueful\Extensions\I18n\Contracts;

interface TranslatorInterface
{
    /**
     * @param array<string, scalar|null> $parameters
     */
    public function trans(string $key, array $parameters = [], ?string $locale = null, string $domain = 'messages'): string;
}

interface LocaleResolverInterface
{
    public function resolveLocale(mixed $context = null): string;
}
```

Core should also provide:

- compatibility with `ServiceProvider::loadMessageCatalogs()`.

Core must not own:

- persisted translation management;
- locale admin UI;
- translation workflows;
- regional formatting rules beyond simple defaults;
- CMS content localization.

### Extension Should Own

`glueful/i18n` owns:

- binding `translation.manager`;
- locale registry;
- translation domains;
- translation keys and values;
- fallback chains;
- missing-translation reporting;
- import/export of translation catalogs;
- optional admin APIs;
- CLI sync and validation tools;
- formatting helpers for dates, numbers, currencies, and regions where practical.

Framework facts this spec relies on:

- `loadMessageCatalogs()` expects files named `messages.{locale}.php`.
- `loadMessageCatalogs()` passes the caller-provided domain into `addMessages()`.
- There is no current core `TranslatorInterface`, so any typed translator contract is a proposed framework addition unless implemented in the extension namespace first.
- Glueful extension providers can declare permissions through `ServiceProvider::permissions()`.

Release sequencing:

- v1 can ship as a standalone extension on `glueful/framework >=1.54.0`.
- It must bind `translation.manager` for the existing catalog hook.
- No framework release is required unless typed translator aliases are later promoted into core.

## Relationship To Lemma

`glueful/i18n` provides the platform localization layer.

Lemma owns content localization:

- localized entries;
- localized field values;
- localized slugs;
- localized routes;
- translation status per entry;
- content fallback behavior;
- editorial translation workflow.

Lemma can depend on `glueful/i18n` for:

- supported locale list;
- fallback chain;
- UI translations;
- field labels and system strings;
- regional formatting.

## Data Model

Suggested tables:

```text
i18n_locales
i18n_translations
i18n_missing_translations
```

### `i18n_locales`

Fields:

- `id` bigint primary auto-increment.
- `uuid` string(12), unique.
- `code` string(16), unique.
- `name` string(255).
- `native_name` string(255) nullable.
- `enabled` boolean default true.
- `is_default` boolean default false.
- `fallback_locale` string(16) nullable, references `i18n_locales.code` in code, no DB foreign key.
- `direction` string(3) default `ltr`.
- `region` string(16) nullable.
- `created_at` timestamp nullable.
- `updated_at` timestamp nullable.

Indexes:

- unique `uuid`.
- unique `code`.
- index `enabled`.
- index `is_default`.

Do not create an `i18n_domains` table in v1. Domains are string namespaces carried on translation rows. A registry table only earns its keep later if an admin UI needs metadata per domain.

### `i18n_translations`

Fields:

- `id` bigint primary auto-increment.
- `uuid` string(12), unique.
- `domain` string(120).
- `locale` string(16), indexed, references `i18n_locales.code` in code, no DB foreign key.
- `key` string(255).
- `value` text.
- `status` string(20) default `active`.
- `source` string(40) nullable.
- `created_at` timestamp nullable.
- `updated_at` timestamp nullable.

Unique key:

```text
domain + locale + key
```

Indexes:

- unique `uuid`.
- unique `(domain, locale, key)`.
- index `(locale, domain)`.
- index `status`.

### `i18n_missing_translations`

Fields:

- `id` bigint primary auto-increment.
- `uuid` string(12), unique.
- `domain` string(120).
- `locale` string(16).
- `key` string(255).
- `first_seen_at` timestamp nullable.
- `last_seen_at` timestamp nullable.
- `hits` integer default 1.

Missing translation tracking should be optional and rate-limited.

Migration notes:

- Register migrations with source `glueful/i18n`.
- Use the default migration tier unless another extension table is referenced.
- Do not create DB foreign keys to user tables or tenant tables.

## Locale Resolution

Resolution order:

1. Explicit locale passed to translator.
2. Request route/query/header override, if enabled.
3. Identity claim `preferred_locale`, if available.
4. Tenant/app locale, if available through a soft dependency.
5. Configured default locale.

Users does not currently guarantee a locale column. User locale should come from identity claims through the existing identity enrichment path, not from a hard dependency on `glueful/users`.

Fallback order:

1. Requested locale.
2. Locale-specific fallback chain.
3. Global fallback locale.
4. Translation key itself.

Locale fallback is a single parent chain plus a global terminal fallback. Ordered fallback lists are deferred. The locale manager must detect fallback cycles such as `fr -> en -> fr` and reject them on write.

## Public API

Primary services:

```php
interface LocaleManagerInterface
{
    public function all(): array;

    public function enabled(): array;

    public function default(): string;

    public function fallbackChain(string $locale): array;
}

interface TranslationRepositoryInterface
{
    public function get(string $domain, string $locale, string $key): ?string;

    public function put(string $domain, string $locale, string $key, string $value): void;

    public function missing(string $domain, string $locale): array;
}
```

`TranslatorInterface` is the stable extension seam. Management services are extension-specific.

## Routes

Optional admin/API routes:

```text
GET    /i18n/locales
POST   /i18n/locales
PATCH  /i18n/locales/{code}
GET    /i18n/translations
POST   /i18n/translations
PATCH  /i18n/translations/{uuid}
GET    /i18n/missing
POST   /i18n/import
GET    /i18n/export
```

Suggested permissions:

- `i18n.view`
- `i18n.manage`
- `i18n.import`
- `i18n.export`

Declare these through `I18nServiceProvider::permissions()` using `Glueful\Permissions\Catalog\Permission::define()`.

Permission enforcement:

- Use an extension-owned route guard/middleware that calls `Glueful\Permissions\PermissionManager::can()` directly.
- Fail closed when the user is missing, the permission manager is unavailable, or permission is denied.
- Do not rely on declarative catalog registration alone; declaration is not enforcement.
- Do not rely on `gate_permissions`/`#[RequiresPermission]` unless the package raises its framework floor to a version where route handler metadata permission enforcement is verified.

## Catalog Loading

The extension should consume catalogs loaded by extension providers through:

```php
$this->loadMessageCatalogs($dir, $domain);
```

Behavior:

- file catalogs use the existing Glueful convention: `messages.en.php`, `messages.fr.php`, etc.;
- persisted translations can override file catalogs when configured;
- sync command can scan file catalogs and create missing DB rows;
- no extension should need to write directly into `i18n_translations`.

## Formatting

Formatting helpers should be optional and dependency-light:

- date/time by locale;
- number formatting;
- currency formatting;
- region display names where available.

Do not make ICU-heavy behavior mandatory unless the PHP environment already supports it.

## Pluralization

Pluralization is part of v1.

- Use ICU MessageFormat when the `intl` extension and required formatter support are present.
- Provide a documented simple fallback for environments without ICU support.
- The fallback should support basic `one`/`other` style messages only.
- Document that complex CLDR plural categories require ICU.

## Caching

Translation lookup is a hot path and must not perform a DB read per call.

Cache translation bundles by:

```text
locale + domain + version
```

Behavior:

- load file catalogs and DB overrides into an in-memory/request cache;
- store merged bundles in the configured cache backend when available;
- invalidate or bump a version fingerprint on translation writes/imports;
- cache misses should fall back to the key and optionally record missing translations;
- missing-translation writes must be rate-limited and should not happen synchronously on every request in production.

## Configuration

Suggested config key: `i18n`.

```php
return [
    'default_locale' => 'en',
    'fallback_locale' => 'en',
    'enabled_locales' => ['en'],
    'missing_tracking' => false,
    'db_overrides_catalogs' => true,
    'cache_ttl' => 3600,
];
```

## Lemma Usage

Lemma can use this extension for:

- available locale list;
- fallback policy;
- admin UI language;
- translated system strings;
- localized validation messages;
- content localization defaults.

Lemma must still own:

- localized content fields;
- localized entry status;
- localized slug uniqueness;
- localized routing;
- translation workflow for entries.

## Testing Requirements

- Default locale resolves when no request/user/tenant locale exists.
- Explicit locale wins over resolver.
- Fallback chain returns the expected value.
- Missing translation returns key and optionally records a miss.
- File catalog translations load correctly.
- DB translations can override file catalog translations.
- Disabled locales are not returned by `enabled()`.
- Locale admin routes enforce permissions.
- Import/export round-trips a catalog.
- Translation bundle caching prevents per-call DB reads.
- Translation writes invalidate the relevant locale/domain bundle.
- Pluralization works with ICU when available and simple fallback otherwise.
- Fallback cycle writes are rejected.
- Permission guard denies when permissions are absent.

## Decisions

1. **Bind the existing hook first.** v1 binds `translation.manager`; typed contracts stay in the extension unless later promoted.
2. **DB overrides file catalogs by default.** This is the point of the extension, backed by bundle caching.
3. **Missing tracking defaults off.** Docs should recommend enabling it in development.
4. **Fallback is single-parent plus global terminal.** Ordered fallback lists are deferred; cycle detection is mandatory.
5. **Pluralization is v1.** ICU when available, simple fallback otherwise.
6. **No `i18n_domains` table in v1.** Domains are strings unless admin metadata later earns a table.
7. **Permission enforcement is extension-owned.** Routes call `PermissionManager::can()` through a guard, not just catalog declarations.
